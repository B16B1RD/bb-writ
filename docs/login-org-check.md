# 専用ログインの組織の確かめ

この文書は、README の [Claude Code の専用ログイン](../README.md#claude-code-の専用ログイン)を用意した人向けに書く。案内が出たときと出ないときの意味と、この確かめに頼れる範囲を説明する。

## 何をするか

bb-writ は Claude Code の子を起動する前に、次の 2 つの組織を比べる。

- 専用ログインのトークンの組織
- bb-writ を呼んだ環境の Claude Code のログインの組織

違えば、子の記録の `claude_login` に案内を出す。問い合わせが終了コード 0 で終わったのに組織を読めないときは、確かめが働いていないことを、同じく記録に案内として出す。

違っても、確かめられなくても、起動は止めない。

入口（指揮者）がその案内を返答で伝えるよう、[`delegate`](../skills/delegate/SKILL.md) のスキルに書いてある。伝えるかは指揮者のモデルしだい。

## 結果の見方

確かめた結果は、子の記録に残る。記録は `~/.local/state/bb-writ/delegations.jsonl` で、Claude Code の子を起動した行の `claude_login` を見る。

案内が返答に無いときも、ここで見られる。`org` が `same` なら、トークンとログインは同じ組織。

## しくみ

トークンの組織を問い合わせるのは、専用ログインの `.env` の中身が変わった後の最初の起動で 1 回だけ。初めての起動と、`claude-login.json` が無い・読めないときも同じ。同時に起こした子は、それぞれ問い合わせる。読めなかったときは、次の起動でまた問い合わせる。

問い合わせでは、専用ログインで Haiku に短い問い合わせをする。問い合わせに `ANTHROPIC_LOG=debug` を付けると、SDK の debug の出力が出る。その出力の全体から、ヘッダー `anthropic-organization-id` の値を探して読む。

Claude Code の文書に `ANTHROPIC_LOG` の記述は無い。根拠は実物（Claude Code 2.1.330、WSL2）と SDK の文書。

ログインの側は、`claude auth status --json` の `orgId` を使う。

覚えるのは、`.env` の中身の SHA-256 と、組織の ID の SHA-256 だけ。置き場は `~/.local/state/bb-writ/claude-login.json`。

## この確かめが守らないこと

- 比べるのは組織で、同じ組織の中の別の人のトークンは見分けない。
- bb-writ を呼んだ環境の `claude auth status --json` の `orgId` が無いときと、uuid の形でないときは比べない。Claude Code にログインしていないときと、環境に `ANTHROPIC_API_KEY` か `CLAUDE_CODE_OAUTH_TOKEN` があるとき（`authMethod` が `api_key`・`oauth_token` になる）は、`orgId` が無い。これは Claude Code 2.1.330 で確かめた（ログインしていないときは空の設定の置き場で、環境の 2 つは偽の値を置いて）。
- 問い合わせの出力から組織を読めないときは、比べない。問い合わせが終了コード 0 で終わっていれば、確かめが働いていないことを案内する。0 でなければ、記録に理由だけを書く。読み方は Claude Code 2.1.330 で確かめた。SDK の debug の出力の書式はバージョンで変わりうると、公式の SDK の文書にある。
- 読めない状態が続く間は、起動のたびに問い合わせる（結果を覚えない）。
- 利用枠で断られた問い合わせ（429）の応答にヘッダーが付くかは、確かめていない（付けば読む）。
- ログインの `orgId` とヘッダーの値が同じだったのを見たのは、1 つのアカウントだけ。
- macOS の実物では確かめていない（確かめたのは WSL2）。
- 別のアカウントのトークンで実際に案内が出ることは、偽の CLI のテストで確かめただけで、実物では確かめていない。
- わざと別のアカウントのトークンを使っているときも、案内は出続ける（止める設定は無い）。
