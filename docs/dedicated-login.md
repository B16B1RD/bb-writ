# 専用ログインの細部

この文書は、README の[任意機能の準備](../README.md#任意機能の準備)で専用ログインを用意した人に向けて書いています。README に書いていない細部と、確かめに頼れる範囲を説明します。

## トークンの組織の確かめ

### 何をするか

bb-writ は Claude Code の子を起動する前に、次の 2 つの組織を比べます。

- 専用ログインのトークンの組織
- bb-writ を呼んだ環境の Claude Code のログインの組織

違えば、子の記録の `claude_login` に案内を出します。問い合わせが終了コード 0 で終わったのに組織を読めないときは、確かめが働いていないことを、同じく記録に案内として出します。

違っても、確かめられなくても、起動は止めません。

入口（指揮者）がその案内を返答で伝えるよう、[`delegate`](../skills/delegate/SKILL.md) のスキルに書いてあります。伝えるかは指揮者のモデルしだいです。

### 案内が出たら

組織が違うという案内が出たときは、子は、そのトークンのアカウントの利用枠で動きます。Claude のアカウントを切り替えたのなら、`claude setup-token` からトークンを作り直します（README の [Claude Code の専用ログイン](../README.md#claude-code-の専用ログイン)）。わざと別のアカウントにしているなら、そのままで構いません。

組織を読めなかったという案内が出たときは、この確かめがいま働いていません。Claude Code のバージョンが変わって、読み方が合わなくなった見込みがあります。Claude のアカウントを切り替えたときは、同じく `claude setup-token` からトークンを作り直します。

### 結果の見方

確かめた結果は、子の記録に残ります。記録は `~/.local/state/bb-writ/delegations.jsonl` で、Claude Code の子を起動した行の `claude_login` を見ます。

案内が返答に無いときも、ここで見られます。`org` が `same` なら、トークンとログインは同じ組織です。

### 仕組み

トークンの組織を問い合わせるのは、専用ログインの `.env` の中身が変わった後の最初の起動で 1 回だけです。初めての起動と、`claude-login.json` が無い・読めないときも同じです。同時に起こした子は、それぞれ問い合わせます。読めなかったときは、次の起動でまた問い合わせます。

問い合わせでは、専用ログインで Haiku に短い問い合わせをします。問い合わせに `ANTHROPIC_LOG=debug` を付けると、SDK の debug の出力が出ます。その出力の全体から、ヘッダー `anthropic-organization-id` の値を探して読みます。

Claude Code の文書に `ANTHROPIC_LOG` の記述はありません。根拠は実物（Claude Code 2.1.330、WSL2）と SDK の文書です。

ログインの側は、`claude auth status --json` の `orgId` を使います。

覚えるのは、`.env` の中身の SHA-256 と、組織の ID の SHA-256 だけです。置き場は `~/.local/state/bb-writ/claude-login.json` です。

### この確かめが守らないこと

- 比べるのは組織で、同じ組織の中の別の人のトークンは見分けません。
- bb-writ を呼んだ環境の `claude auth status --json` の `orgId` が無いときと、uuid の形でないときは比べません。Claude Code にログインしていないときと、環境に `ANTHROPIC_API_KEY` か `CLAUDE_CODE_OAUTH_TOKEN` があるとき（`authMethod` が `api_key`・`oauth_token` になる）は、`orgId` がありません。これは Claude Code 2.1.330 で確かめました（ログインしていないときは空の設定の置き場で、環境の 2 つは偽の値を置いて）。
- 問い合わせの出力から組織を読めないときは、比べません。問い合わせが終了コード 0 で終わっていれば、確かめが働いていないことを案内します。0 でなければ、記録に理由だけを書きます。読み方は Claude Code 2.1.330 で確かめました。SDK の debug の出力の書式はバージョンで変わりうると、公式の SDK の文書にあります。
- 読めない状態が続く間は、起動のたびに問い合わせます（結果を覚えません）。
- 利用枠で断られた問い合わせ（429）の応答にヘッダーが付くかは、確かめていません（付けば読みます）。
- ログインの `orgId` とヘッダーの値が同じだったのを見たのは、1 つのアカウントだけです。
- macOS の実物では確かめていません（確かめたのは WSL2）。
- 別のアカウントのトークンで実際に案内が出ることは、偽の CLI のテストで確かめただけで、実物では確かめていません。
- わざと別のアカウントのトークンを使っているときも、案内は出続けます（止める設定はありません）。

## 子が Fable を使えないとき

bb-writ が立てる子が Fable を使えないときに launcher が子を立て直す動きは、[`delegate`](../skills/delegate/SKILL.md) の「モデルと effort」にあります。ここには、delegate に書いていないことだけを書きます。

- 立て直すのは、利用枠が尽きた（429）か使えないモデル（404）の API のエラーのときだけです。ほかの API のエラー（過負荷・回線・認証）では立て直しません。
- Fable を使えない専用ログインそのものと、利用枠が尽きた専用ログインそのものでの立て直しは、確かめていません。
- Fable を使えない専用ログインで push・PR まで頼む使い方は、確かめていません。
- 組織の制限などで頼んだモデルと違うモデルで動いた子に `model_substituted` を残すことは、実物では確かめていません。
- 専用ログインの設定の `availableModels` が Fable を外していても、launcher の子は `--restricted` で動くので、Fable のまま動きました。
