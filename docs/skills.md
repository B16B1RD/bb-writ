# スキルの使い方

[はじめての bb-writ](getting-started.md) を読み終えた人に向けて、自分で呼ぶスキルの使い方を 1 本ずつ説明します。各節は、使う場面・頼み方・準備・返ってくるもの・使わない場面の順に並んでいます。スキルが中でたどる手順は、各節の最後のリンク先（スキルの本文）にあります。

例は Claude Code の書き方です。Codex では先頭の `/` を `$` に変えます（`$bb-writ:interrogate`）。Grok Build では `/<スキル名>` と入力します（`/interrogate`）。例のリポジトリ名・番号・パスは、手元のものに置き換えます。

## 1. どれを自分で呼ぶか

スキルの一覧には、手引きと原則を含むすべてのスキルが並びますが、自分で名前を打つのは次の 7 本です。

| スキル | 使う場面 | 準備 |
|---|---|---|
| `bb-writ` | 技術的な仕事をすべて、ここから頼む | なし |
| `unknowns` | 何を作るか・どの案にするかが決まっていない | なし |
| `interrogate` | 変更・設計・計画の穴を、独立した審査役に探させる | 別の CLI と専用ログインがあれば、別系統の審査役も立てる（無ければ同じ CLI で代える。Codex では Codex の専用ログインが要る） |
| `playbook-eval` | スキル・設定・モデルの変種を、同じ依頼で比べる | 別の CLI と専用ログイン |
| `reflect` | 仕事の区切りで、繰り返し効く学びを取り出す | 別の CLI と専用ログイン |
| `correct` | 同じ誤りを繰り返すので、起こせない形にリポジトリを変える | なし |
| `create-verification-skill` | 対象のリポジトリに、成果物の確かめ方をスキルとして残す | 対象がスキルのときは、新しい CLI セッションを起動できること |

ほかのスキルは、入口の `bb-writ` が依頼に合わせて選んで使います。名前を打つ必要はありません（[9 節](#9-入口が中で使うスキル)）。

「別の CLI と専用ログイン」は、使っている CLI 以外の CLI（Claude Code・Codex・Grok Build のうちどれか 1 つ）を、bb-writ だけが使うログインで起動するための準備です。手順は README の [任意機能の準備](../README.md#任意機能の準備) にあります。Codex で `interrogate` を使うときに要る Codex の専用ログインも、同じ節にあります。

## 2. bb-writ（入口）

**使う場面：** 調べる・直す・足す・文書を書く・PR を出す・続きをやる、のすべてです。迷ったら、ここから頼みます。

**頼み方：** 依頼文に、目的と、どこまで進めてよいかを書きます。進める範囲の書き方は [はじめての bb-writ の 4 節](getting-started.md#4-進める範囲を依頼文で決める) にあります。

```text
/bb-writ:bb-writ ログイン後にトップへ戻らない。直して。
```

**返ってくるもの：** 依頼の言い直し（目的・制約・確かめ方）、何をしたか、何を実行してどの結果を見たか、残る範囲、自分で確かめるためのコマンドかパス。残る範囲には、返す前に新しい文脈の子が「閉じる手段が無い」と判定したもの（この環境で実行できないこと、決まらない選択、push などの許可）だけが載ります。

**使わない場面：** 何を作るかが決まっていないとき。入口は依頼を受けるとすぐに進むので、先に `unknowns` で探索します。

[入口の本文](../skills/bb-writ/SKILL.md)

## 3. unknowns（実装の前の探索）

**使う場面：** 作りたいものはあるが形が決まっていない、案が複数ある、何を聞けばよいかも分からない、というときです。探索の間、`unknowns` はコードを変えません。

**頼み方：** 曖昧なままで構いません。知っていること・決めていることがあれば添えます。

```text
/bb-writ:unknowns 設定画面にダークモードを足したい。どこまでやるべきか分からない。
```

`unknowns` は状況を見て、次の 4 つのやり方を組み合わせます。どのやり方で進めるかは、始めに `unknowns` から伝えます。「まず案を 3 つ出して」のように、やり方を指定することもできます。

- **見落としの洗い出し：** リポジトリと Web を調べ、考慮していなかった事項を、知らずに進むと高くつく順に並べます。
- **案の比較：** 性格の違う 3〜5 案を、手軽な案から野心的な案の順に並べます。どれかを選ぶより、「A の手軽さは欲しいが B のこの部分も欲しい」のように反応すると、言葉にしていなかった要件が表に出ます。
- **使い捨ての試作：** 見た目で決まることは、仮のデータで動く HTML のページにして見せます。Artifact を使える環境では Artifact で、使えなければ HTML ファイルのパスで届きます。ページの区画ごとに「このまま / 要調整」とコメントを付けられ、まとめた文をチャットに貼り付けて返します。動かせば決まること（速さ・出力の形）は、使い捨てのスクリプトで測って決めます。
- **質問：** 好み・優先度のように、調べても決まらないことだけを、推奨案を付けて 1 問ずつ聞きます。

**返ってくるもの：** 最後に「探索サマリ」が出ます。確定したこと、却下した案とその理由、問いの決着記録（調査・実験・回答・仮決定・後回しのどれで閉じたか）、検証タスク（手順・合否基準・結果ごとの分岐）、残った問い、見つかった盲点、次のステップです。問いを残したまま終わらないように、浮かんだ問いはすべてどれかの方法で閉じてから出します。

**サマリの後：** 同じセッションで入口に渡します。

```text
/bb-writ:bb-writ この探索サマリのとおりに作って。検証タスクも実行して。
```

別のセッションで進めるときは、「このサマリを `notes/dark-mode.md` に保存して」と頼み、新しいセッションでそのファイルを示します。

**使わない場面：** 仕様が決まっている実装（入口に頼みます）。既存のコードがどうなっているかを調べるだけの依頼（入口に「調べて。変更しないで」と頼みます）。

[unknowns の本文](../skills/unknowns/SKILL.md)

## 4. interrogate（独立した審査）

**使う場面：** 自分や同僚の変更、設計の文書、計画に、見落としが無いかを確かめたいときです。審査役を 2 人立てて敵対的に読ませ、指摘を突き合わせ、主審として判定します。

**頼み方：** 何を審査するかを指します。ブランチ・ファイル・設計の文書のどれでも構いません。

```text
/bb-writ:interrogate main からこのブランチまでの変更を審査して
/bb-writ:interrogate docs/design/cache.md の設計を審査して。src/cache/ の今のコードとも照らして
```

対象のリポジトリに審査の指針（`REVIEW.md` など）があれば、審査役に読ませます。Issue に受入条件が並んでいれば、1 行ずつ審査の意図に写し、それぞれを確かめる試験があるかも見させます。審査役には指摘とは別に、試験で落ちない退行の注入を全部挙げさせます。条件の中で並べた欄や許す値の一覧があれば、1 つずつ落として、落とす試験があるかを表にさせます。

**準備：** 審査役の 1 人は同じ CLI の新しい文脈、もう 1 人は別の CLI です。別の CLI と専用ログインが無ければ、同じ CLI の新しい文脈をもう 1 人立て、その旨を報告に書きます。Codex では、同じ系統の審査役も別プロセスの Codex として起動するので、Codex の専用ログインが要ります。

**返ってくるもの：**

1. 審査の意図（何を満たすべき変更か）
2. 審査役ごとの CLI・モデル・指摘の数・起動の結果
3. 指摘の判定。「対応する」（実害があり、実物で確かめたもの）、「検討」（正当だが直す費用に見合うか、利用者が決める）、「記録のみ」、「退ける」（理由つき）の 4 つ
4. 審査役の意見が一致した所と割れた所

**頼んだ審査では直さない：** `interrogate` を自分で呼んだときは、指摘を報告するだけで、ファイルを変えません。直すときは、続けて入口に頼みます。

```text
/bb-writ:bb-writ さっきの審査の「対応する」をすべて直して
```

入口がコードを変えたときは、届ける前に入口が自分で `interrogate` を通します。このときは「検討」を使わず、直すかどうかを入口が決めます。審査の深さは変更の危険度で決まり、文言だけの変更なら省き、認証・課金・データの削除などは 2 人に見せます。

**使わない場面：** 文章の読みやすさの添削。`interrogate` が攻めるのは、変更が意図を満たすかどうかです。

[interrogate の本文](../skills/interrogate/SKILL.md)

## 5. playbook-eval（目隠しで比べる）

**使う場面：** スキルや指示ファイルの 2 つの版、2 つのモデル、2 つの設定のどれがよいかを、同じ依頼で走らせて決めたいときです。

**頼み方：** 比べるものと、何をもって「よい」とするかを書きます。基準を書かなければ、`playbook-eval` が 3〜6 項目の基準を立てます。

```text
/bb-writ:playbook-eval 今の CLAUDE.md と、テストの節を書き直した CLAUDE.new.md を比べて。日付の不具合を直す依頼で、どちらが試験を先に書くか測って
```

**準備：** 別の CLI と専用ログインが要ります。判定を、候補と別の系統の審査役が受け持つからです。

**どう比べるか：**

- 候補（比べられる側の CLI）に、測られていることを悟らせません。依頼文は普段打つ 1〜2 文にし、作業場所や依頼文に「比較」「評価」などの語や変種の名前を入れません。
- 候補ごとに、同じ状態の写しで同時に走らせます。写しにはリモートを付けないので、push や PR は起きません。
- 成果物を外から確かめる「隠した試験」を先に書き、候補の成果物に実行します。
- 審査役は、候補を記号でだけ見ます。モデル名や変種名は伏せます。

**返ってくるもの：** 比べた変種、基準、候補ごとの所見（隠した試験の結果・時間・費用）、審査役の判定、まとめ、どちらを採るかの推奨とその根拠。1 回の実行で決まらないことは、そう書かれます。揺れを測るには、回数を重ねて頼みます。

**使わない場面：** 1 つの変更が正しいかどうかの確認（`interrogate` を使います）。

[playbook-eval の本文](../skills/playbook-eval/SKILL.md)

## 6. reflect（振り返り）

**使う場面：** 大きめの仕事が終わった区切りや、同じ訂正を 2 回したときです。次の仕事でも同じ誤りや遠回りを生む原因を取り出し、効く場所に送ります。

**頼み方：**

```text
/bb-writ:reflect この PR の仕事を振り返って
```

**準備：** 別の CLI と専用ログインが要ります。材料の要約を、同じ CLI の新しい文脈と別の CLI の 2 人に、独立に読ませるからです。`interrogate` と違い、別の CLI が無いときの代わりの手段は、スキルの本文に書かれていません。別の CLI が無い環境で `reflect` がどう振る舞うか（止まるのか、同じ CLI だけで進むのか）は、まだ確かめていません。

**材料：** この会話、作業場所の記録、PR の本文とレビューのコメント、利用者からの訂正、落ちた検査とその直し方です。ほかのセッションの会話は探して読みません。

**返ってくるもの：** 学びの候補を 3 つに分けた一覧です。

- **採る：** 2 回以上起きた、または起きれば被害が大きいもの。行き先と形が付きます。
- **退ける：** 1 回きり・根拠が無い・既に仕組みで防がれているもの。
- **後で：** 正当だが、防ぐ手段をいまの仕事の中で作れないもの（別のリポジトリや別の担当の持ち物）。どこに積むかが付きます。

学びの行き先は 2 つです。対象のリポジトリに関する学び（そのリポジトリの事実や経験則）は、そのリポジトリへの変更として入口の流れで出します。bb-writ 自身の振る舞いに関する学びは、変更の案を示して、利用者の承認を待ちます。形は、注意書きを足すより強いもの（作りを変える・型・lint・試験）を先に選びます。

**使わない場面：** 1 回きりの失敗の反省。`reflect` は 1 回きりの出来事を学びにしません。

[reflect の本文](../skills/reflect/SKILL.md)

## 7. correct（繰り返す誤りを起こせなくする）

**使う場面：** エージェントが、このリポジトリで同じ種類の誤りを何度も起こすときです。注意書きを足すのでなく、誤りを起こせない形にリポジトリを変えます。

**頼み方：** 誤りの例を添えると、種類を絞りやすくなります。

```text
/bb-writ:correct 日付の整形を src/utils/date.ts を通さずに書く誤りが何度も起きる。起こせないようにして
```

誤りを指さずに頼むと、`correct` は最近の commit・revert・レビューのコメント・指示ファイルから、2 回以上起きた種類を探します。

**直し方：** 種類ごとに、効く最も高い段で直します。

1. **作りで無くす：** 正しい道を 1 つにし、古い道と使われないコードを消します。
2. **検査で書けなくする：** lint か CI の検査を足し、エラー文に代わりに使うものを書きます。
3. **試験を直す：** 振る舞いが壊れても通る試験と、内部を変えただけで落ちる試験を直します。
4. **指示を書く：** 判断が要るものだけを、指示として書きます。

足した検査は、過去の実際の誤りで落ちることを示します。たとえば、誤りを直した commit を revert して誤りが残る状態に戻し、検査が落ちる出力を見せます。指示ファイル（`AGENTS.md` など）には、規則とそれを強制するものの表を置き、保ちます。

**返ってくるもの：** 種類ごとの根拠、選んだ段、それより高い段を選べなかった理由、検査が落ちることを示した出力。直しは 1 種類 1 commit です。push や PR は、依頼文に書いた範囲で出します。

**使わない場面：** 1 回だけの誤りの修正（入口に「直して」と頼みます）。学びを見つけるところから始めたいとき（`reflect` が先です）。

[correct の本文](../skills/correct/SKILL.md)

## 8. create-verification-skill（確かめ方をスキルにする）

**使う場面：** 「できた」を毎回同じ方法で確かめたいリポジトリで、その方法をスキルとして残すときです。たとえば、CLI を実際に起動して出力を見る、画面を開いて操作する、文書の手順をそのまま実行する、などです。入口が検証の途中で「繰り返し使える確かめ方が無い」と判断したときも、入口から使われます。

**頼み方：**

```text
/bb-writ:create-verification-skill このリポジトリの CLI の確かめ方をスキルにして
```

**準備：** 対象がスキルのときは、新しい CLI セッションでスキルが使われるかを観測するので、新しいセッションを起動できる必要があります。ほかの対象では要りません。

**作られるもの：**

- `.agents/skills/verify-<対象>/SKILL.md`（Codex が読む置き場）と、`.claude/skills/verify-<対象>` からの symlink（Claude Code が読む置き場）。本文は、準備・点検・操作・証拠・壊して確かめる・片付けの 6 節です。
- 同じ `.agents/skills/verify-<対象>/` の下の `features/` に、利用者から見た主な機能 3〜5 個の確かめ方。

作った後、新しい文脈で最初から 1 回通し、成果物に欠陥を 1 つ入れた写しで検査が落ちることを確かめます。この 2 つを見るまでは完成と呼ばず、「下書き」として返ります。

**届け方：** そのリポジトリの通常の方法（PR など）で届けます。本文には、作ったスキルの場所、1 回通したときのコマンドと結果、壊した例が落ちた出力、確かめていない機能が書かれます。push や PR は、依頼文に書いた範囲で出します。

**使わない場面：** 1 回だけの確かめ（入口が直接確かめます）。

[create-verification-skill の本文](../skills/create-verification-skill/SKILL.md)

## 9. 入口が中で使うスキル

次のスキルは、入口の `bb-writ` が依頼と局面に合わせて呼びます。名前を打たずに、入口に普通の言葉で頼みます。手引きは入口から呼ばれる前提で書かれていて、本文には依頼の言い直しも、書く前の作業場所の確保もありません。

### 手引き

| スキル | 入口が使うとき | こう頼むと使われる |
|---|---|---|
| `playbook-investigation` | 読んで答える依頼。何も変えない | 「調べて。変更しないで」「なぜこうなっている」 |
| `playbook-bug` | 不具合を直す。再現してから原因を絞る | 「〜にならない。直して」 |
| `playbook-feature` | 振る舞いを足す・変える | 「〜を足して」「〜できるようにして」 |
| `playbook-docs-skill` | README・手引き・SKILL.md を書く・直す | 「README のこの節を直して」 |
| `playbook-parallel` | 書く前に、タスク専用の作業場所（Git の worktree）と担当を取る。統合と片付けも | 書く依頼のすべて |
| `playbook-pause-safely` | 区切りで止め、続きを再開できる状態にする | 「いったん止めて」 |
| `playbook-session-pickup` | 前のセッションの続きを、記録と実物から引き受ける | 「続きをやって」「PR #34 の続き」 |

止める・続ける・任せて離れるの頼み方は、[はじめての bb-writ の 8 節](getting-started.md#8-途中で止める続きをやる任せて離れる) にあります。

### 原則

`principle-*` は、入口が仕事の局面に当たるものだけを読む判断の基準です。入口の返答に「判断を変えた原則」が書かれることがあります。

| 局面 | 原則 |
|---|---|
| 依頼を受けた | `principle-two-human-roles`（人間の役割は要件を伝えることと完成品を確かめることの 2 点）・`principle-never-block-on-the-human`（戻せる作業は聞かずに進める）・`principle-experience-first`（利用者が得る結果から考える） |
| 形を決める | `principle-foundational-thinking`（データの形と土台から決める）・`principle-model-the-domain`（規則を分岐でなく構造に入れる）・`principle-no-speculative-structure`（将来に備えた構造を足さない）・`principle-single-user-machine`（1 人の開発機を前提にする） |
| 変更を書く | `principle-laziness-protocol`（最小の変更で解く）・`principle-subtract-before-you-add`（足す前に削る）・`principle-fail-loud`（黙って既定値で続けず、止める）・`principle-sequence-verifiable-units`（確かめられる単位で順に進める） |
| 行き詰まった | `principle-fix-root-causes`（症状でなく原因を直す）・`principle-attack-the-premise`（同じ前提の修正が 2 回落ちたら前提を疑う）・`principle-no-budget-cap-on-quality`（回数や時間の上限を理由に未完成を完成と呼ばない） |
| 試験と完了 | `principle-test-behavior-not-implementation`（実装でなく振る舞いを試験する）・`principle-prove-it-works`（実物で確かめる） |
| 終わった後 | `principle-encode-lessons-in-structure`（教訓は文でなく構造にする）・`principle-route-lessons`（知見を効く場所に置く） |

### そのほか

- `delegate`: 子への委任と、別の CLI を専用ログインで起動する呼び出し方。`interrogate`・`playbook-eval`・`reflect` が別の CLI を使うときの土台です。準備は README の [任意機能の準備](../README.md#任意機能の準備) にあります。
- `verify-parallel`: bb-writ 自体を開発する人が、作業場所の分離と統合を実際の CLI で確かめるためのスキルです。利用者は使いません。

## 10. 通し例：1 つの仕事を最後まで

検索の結果を一時保存（キャッシュ）する機能を足す仕事で、スキルがどうつながるかを示します。

1. **探索する。** 何をどこまで保存するかが決まっていないので、`unknowns` から始めます。

   ```text
   /bb-writ:unknowns 検索が遅い。結果をキャッシュしたいが、どこまでやるべきか分からない。
   ```

   見落としの洗い出し（古い結果を返す期間、メモリの上限）と案の比較を経て、探索サマリが出ます。サマリの検証タスクには、たとえば「同じ検索の 2 回目が 50 ms 以内に返るか測る」のような手順と合否基準が入ります。

2. **作る。** サマリを入口に渡します。

   ```text
   /bb-writ:bb-writ この探索サマリのとおりに作って、ドラフト PR まで。検証タスクも実行して。
   ```

   入口は作業場所を取って作り、検証タスクを実行します。コードを変えたので、届ける前に自分で `interrogate` を通し、指摘を直してからドラフト PR を出して止まります。

3. **範囲を絞って審査を頼む。** 入口の審査とは別に、気になる所を指して審査を頼めます。

   ```text
   /bb-writ:interrogate PR #34 の変更のうち、キャッシュの失効の扱いを審査して
   ```

   報告の「対応する」を直すなら、4 節と同じく、入口に「さっきの審査の「対応する」をすべて直して」と頼みます。

4. **マージする。** PR を読んで問題がなければ、入口に頼みます。

   ```text
   /bb-writ:bb-writ PR #34 を承認した。マージして
   ```

5. **振り返る。** 仕事の中で、テストの書き忘れを 2 回指摘したとします。

   ```text
   /bb-writ:reflect この PR の仕事を振り返って
   ```

   「キャッシュの層に試験を書かずに進めた」が「採る」に入り、行き先と形が示されます。

6. **起こせなくする。** 同じ誤りがこのリポジトリで続くなら、`correct` に渡します。

   ```text
   /bb-writ:correct キャッシュの層を試験なしで足す誤りが続く。起こせないようにして
   ```

   `correct` は、たとえば「`src/cache/` の変更に試験の変更が伴わなければ CI で落とす」検査を足し、過去の実際の commit で落ちることを示します。
