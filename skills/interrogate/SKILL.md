# interrogate: 独立した審査の panel

審査役を 2 人立てて変更を敵対的に読ませ、指摘を突き合わせ、自分が主審として判定する。価値は役割の演技でなく、文脈とモデルの系統の違いから来る。審査役の報告は主張であって事実ではない。主審は実物で確かめてから判定する。

## 1. 範囲を決める

- 利用者が指したファイルや差分があればそれ。作業ブランチなら基点からの差分（`git diff <基点>...HEAD`）。計画や設計なら、その文書と関係するコード。
- 審査役は自分でリポジトリを読むので、差分を貼り付けるより「どの範囲をどのコマンドで見ればよいか」を渡す。

## 2. 意図を書く

依頼・commit・PR の本文・コードから、変更の意図を 1 段落で書く。審査役には「意図そのものは疑わず、実装が意図を満たすかを攻めよ」と渡す。意図が読み取れなければ、その不明点も審査の対象にする（人間に聞いて止まらない）。

## 3. 審査役を立てる

同じ依頼文を 2 人に渡す。

- **審査役 A（同じ系統・新しい文脈）:** Claude Code では `Agent` ツール（読み取り専用の探索型）。Codex では launcher の `--host codex`。Codex の workspace-write の sandbox の中では入れ子の `codex exec` が起動できず、非対話実行ではサブエージェントも起動されなかった（2026-10-17 の実測）。起動できなければ「同系統の審査は無い」と書き、B だけで判定する。
- **審査役 B（別系統）:** launcher で、もう一方の CLI を bb-writ 専用のログインで、読み取り専用で起動する。

  ```bash
  # Claude Code から Codex を（${CLAUDE_PLUGIN_ROOT} はプラグインの置き場）
  python3 "${CLAUDE_PLUGIN_ROOT}/scripts/launch.py" --host codex --cwd <対象> --prompt-file <依頼文のファイル>
  # Codex から Claude Code を（このスキルの SKILL.md から 2 つ上の scripts/launch.py）
  python3 <プラグインの置き場>/scripts/launch.py --host claude --cwd <対象> --prompt-file <依頼文のファイル>
  ```

  launcher は 1 行の JSON を返す。`status` が `ok` のときだけ報告を使う。`invalid-report`（結論・証拠が無い、証拠のファイルが無い）・`failed`・`quota`・`unavailable` は、その理由を判定の記録に書く。別系統が使えなければ、同じ系統の新しい文脈をもう 1 人立て、「別系統の審査は無い」と書く。利用枠が尽きても、別料金の API へ黙って切り替えない。

依頼文に入れるもの:

- 意図の段落と、見る範囲（コマンドとパス）。
- 観点: 正しさ（空・境界・異常系・二重実行・中断後の再実行・並行）、症状でなく原因を直しているか（guard や再試行で隠していないか）、構造（検証は境界で 1 回か、データの形が使われ方に合うか、後付けに見えないか）、試験（振る舞いを確かめるか、壊したら落ちるか）、利用者から見た結果。
- 指摘ごとに: 重さ（`critical` 壊れる / `warning` 後で痛む / `nit` 好み）、場所（ファイル:行）、何が悪いか、根拠（呼び出しの経路をたどって示す）、代案があれば。ほめない。何も無ければ「指摘なし」。

## 4. 突き合わせる

- 同じ問題を別の言い方で挙げた指摘をまとめ、誰が挙げたかを残す。2 人が独立に挙げた指摘が最も強い。
- 1 人だけの指摘も読むが、重みを下げる。片方が問題と言い、もう片方が明示的に問題ないと言う箇所は、判定の材料として残す。

## 5. 主審として判定する

中立の集計係でなく、実用を重んじる主審として、全指摘を 4 つに分ける。「対応する」に入れる指摘は、主審が実物（コード・実行）で確かめてから入れる。

- **対応する:** 正しさ・安全・保守に実害がある。実際の PR なら止める。
- **検討:** 正当だが、いま直す費用に見合うか分からない。利用者の判断に値する。
- **記録のみ:** 正しいが、いまは行動に移さない（状況次第、早すぎる最適化、影響が小さい）。
- **退ける:** 誤り・些末・文脈の欠落。理由を 1 文で。

## 返す形

1. 意図（2 の段落）。
2. 審査役: A と B のホスト・モデル（launcher の `model_effective`。分からなければ「不明」）・指摘の数・launcher の `status`。
3. 対応する / 検討 / 記録のみ / 退ける（各指摘に、挙げた審査役と 1 行の理由。対応するには確かめた方法）。
4. 一致と相違: どこで一致し、どこで割れ、それが何を示すか。

変更は自動で入れない。利用者が「直して」と言えば、入口 `bb-writ` から直す。
