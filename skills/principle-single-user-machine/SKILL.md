# 単一ユーザーの開発機を前提にする

bb-writ とそのスキルは、1 人の開発者の機械で動く。共有ホストやマルチテナント向けの敵対的な堅牢化（TOCTOU の徹底防御、squat 対策、他ユーザーからの攻撃の想定）は、実測付きの指摘であっても求めない。

**なぜ:** 守る相手がいない防御は費用だけ増やす。本当に要るのは、自分の子プロセス同士の競合（並行する作業の衝突、二重書き込み）と、自分の資格情報・個人設定が別の仕事に混ざらないこと。

**適用する場面:**
- ロックや排他を設計するとき（守るのは自分の並行作業）。
- 専用ログインや作業領域の分離を決めるとき（守るのは費用の帰属と設定の混入）。
- レビューで「悪意ある入力」「他ユーザー」を想定した指摘が出たとき。

**やること:**
- 並行する子の競合・応答喪失・二重書き込みは機械で防ぐ（排他、照合、再開の記録）。これは単一ユーザーでも起きる。
- 資格情報の分離はホストの正式な機能（専用の設定ディレクトリ、worktree、権限モード）で行い、独自の隔離基盤を作らない。
- 敵対的な堅牢化の指摘は、観察として記録し、差し戻しにしない。

**使わないとき:** 会社のリポジトリや共有の環境で、組織の権限制御が要求されている場合。その制約はホストと対象側の規則に従う。

**確かめる例:** 排他・照合の試験が「自分の並行プロセス」を対象にしている。「攻撃者」を想定したコードや文が差分に無い。
