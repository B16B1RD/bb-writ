# 足す前に削る

系を育てるときは、先に複雑さを取り除き、それから作る。既定は削る方。見つけたときより少し単純で、できることは同じか多い形を、同じか小さい表面で残す。

**なぜ:** 削った後の土台は読みやすく、足す変更も小さく済む。不要なものの上に足すと、不要なものとの整合まで保ち続けることになる。

**適用する場面:**
- 新しい機能を入れる場所の近くに、使われていない関数・設定・分岐があるとき。
- 書き直しや移行を始めるとき。
- スキルや手引きの文に、重複した指示・中身の無い参照・長すぎる雛形があるとき。

**やること:**
- 順番を、削る → 作る、にする。削るだけの commit を先に置く。
- 磨く前に切る。最小の形に達してから、品質に手をかける。
- 実際の使われ方に合わせて作る。仕様が求める以上の検証・解析器・防御を足さない。新しい内容の無い参照は、空の見出しを残さずに消す。

**使わないとき:** 消す対象がまだ使われている場合。呼び出し元を移してから消す（`principle-no-speculative-structure` の旧 API の扱い）。

**確かめる例:** 最初の commit が削除で、機能の commit がそれに続く。変更の後で、ファイルや公開する関数の数が増えていない。増えたなら理由が書いてある。
