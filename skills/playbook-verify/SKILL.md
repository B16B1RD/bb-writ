# 手引き: verify（確かめて返す）

会話が要約された後は、入口の本体 `bb-writ:conduct` を呼び直して全文を読み直す（`bb-writ:bb-writ` は呼び直さない）（要約の後は、先に呼んだ入口が落ちていることがある）。

入口の「検証」の (1)〜(6) は要点だけで、ここが全文。

## 確かめる

下の「検証」の、その対象の形で確かめる。対象のリポジトリに検証スキル（`verify-*`）があれば、それに従う。無く、同じ確かめ方を繰り返し使いそうなら `create-verification-skill` で作る。対象のリポジトリにある検査のうち、変更が影響する範囲のもの（文書なら文書の検査、コードなら該当のテストと lint。CI と同じコマンド）は、変更が小さくても手元で実行する。変えた事実（値・条件・状態・名前）を前提にしている記述は、差分の外まで探して読む。同じリポジトリの別の文書の要約文や、変えたコードを説明するコメント・テスト名・assert のメッセージのこと。変えた語・アンカー・リンク先で検索し、食い違えば同じ変更で直す。レビュー対応の直しでも同じにする。検査は、差分の外の文が古くなったことを捕まえない。変更が規則を決める（差分の外の箇所も従うべき決まりを足す・変える）ときは、危険度が低で `interrogate` を通らない変更でも、指揮者が、決めた規則を 1 文ずつ書き出し、規則ごとに、既存の同じ種類の箇所・同じ種類の項目を守る検査・その規則に関わる指摘を出すツールの設定の 3 種類の当てはめ先を検索で探し（それぞれの見方は `interrogate` の 1 の (i)〜(iii)）、探したコマンドと、見つけた場所か「無し」を、作業の記録の「済んだことと証拠」に書く。見つけた食い違いと検査の欠けは、下の「成果物の検証」の指摘の仕分けと同じに扱う。同じ変更の途中で範囲を広げた（振る舞い・検査・節を足した）ら、その commit の後に、同じ変更の中で「この変更でしたこと」を並べた文を拾い直す。前の commit で自分が書いた作業記録の表の行・文書の要約・CHANGELOG の節と、その変更の PR の本文のこと。`git diff <基点>...HEAD` と PR の本文（`gh pr view <番号> --json body`。git の差分には出ない）を、変更を指す識別子（Issue・PR の番号）と、前の commit で書いた要約の語で探し、足した分を欠けば同じ変更で書き足す。誤りを書いていない要約も、欠けていれば直す対象にする。足したのが新しい振る舞いなら、変えた語で探しても要約は見つからない。外部のサービスの挙動に頼る主張（前の決定・出典から流用した理由を含む）は、主審が実物（実際の実行結果・公式の文書）で確かめる（審査役は確かめられない。`interrogate` の 5）。足したテスト・検査は、流した出力のケースの名前・失敗のメッセージを、人が読む文として読む（書式の指定（`%s`・`{}` など）がそのまま残っていないか、どの場合を確かめるかが名前から読めるか）。同じ成果物に対する有効な既存の検証結果は、取り直さずに再利用する。「ビルドが通った」「テストが通った」だけを完成の根拠にしない。

## 検証

信じてよい条件: (1) 何が観測できれば成功かを、依頼・既存仕様・実物の利用箇所から先に定める。通るように後から弱めたら「同じ条件を満たした」と報告しない。(2) 新しい自動検査は、正しい例に加え、対象の欠陥を入れた例または既知の失敗例で落ちることを確かめる。欠陥の例には、検査が見る語を残したまま意味を後退させる例と、既知の古い形（出典の古い記述・前の版）から作る例を必ず含める。語を消す例だけでは、語の有無と順だけを見る検査も通ってしまう。(3) 意味の判断が残れば、別セッションに目的・実物・反例を渡す（`delegate` の launcher で読み取り専用に立てる。`Agent` の子の書き込みは OS で止まらない）。作者の成功報告だけを読ませない。対象のリポジトリにある別の役の agent（設計の文書との整合を見る役など）は、役割が意味の判断でなければ代わりにならない。別モデルが通したことを機械的な証明にしない。(4) 未実行・環境不足・結論の出ない部分は、その範囲を残す（閉じられるものは閉じてから。入口の「返答の形」の 4）。CI が無ければ「CI なし」としてローカルの結果から判断し、対象に必須の CI があればその結果も待つ。小さな訂正では既存の確かな検証を再利用する。ただし、主張を足す・変える訂正は、1 行でも再利用しない。その主張を縛る検査があるかを確かめ、無ければ (2) の形で足す。(5) 新しい自動検査を足す変更と、検査の期待値を変える変更では（下の「前例を写す変更」を除く）、push・PR の前に、新しい文脈の子 1 人に、意図・検査・その主張の出典・後退の一覧だけを渡し、次の 4 つを頼む（起動は `delegate` の launcher）。(a) 意図の主張を、今の出典の、その主張を定める節の全文と照らし合わせ、抜けた限定・例外を挙げる。主張を正しいものとして渡さない。出典を超える主張は、検査を足さずに出典まで狭める。(b) 後退の一覧の行を 1 つずつ注入し、検査が落ちるか。一覧に無い後退の出所が 3 つの中にあれば、行を足す。(c) 主張を保ったまま検査を落とす書き換え（誤検出）。(d) 出典の現象が起きるのに、検査が当たらない入力（見逃し）を挙げる。出典の環境が手元に無ければ、先に、その現象を手元で再現する場を作れるかを試す。意図には、その検査が守る範囲の主張をすべて書く。依頼（Issue など）に MUST・受入条件が並んでいれば、1 行ずつ写し、行ごとに守る検査（無ければ無い）を添える。後退の一覧は最初の子を立てる前に書き、出所は 3 つだけにする。前の版（変えた hunk を戻す）、出典の古い記述、手で並べた要素（分岐・許す値・比べ方・境界の文字。分岐ごとに書いた同じ条件は、それぞれ別の要素）を 1 つずつ落とす・緩めるもの。一覧の行が通ったら検査を直し、直した commit で新しい子に、一覧の行が落ちることと、直しの差分（前に通した commit から直した commit まで）を `interrogate` の 3 の観点で読むことだけを頼む（新しい後退は探させない。`--interrogate` は付けない。テストだけの直しの差分は危険度が低で、届けるときは `--delta 低`。`interrogate` の 5）。直しで足したテストの名前・メッセージにも誤りが入る（`printf` の書式をそのまま埋め込んだケース名を、「防ぐか」だけを確かめた 2 周の子も書き手も、出力に写したまま挙げなかった）。一覧の外で子が見つけた書き換えは、検査を足さず、守らない範囲をリポジトリの中の文（テストの名前・コメント・文書）に書いて閉じる。PR の本文はマージの後に読まれない。(d) で挙がった見逃しは、入口の「その場で」の審査の指摘と同じに分ける。普段の利用で起こる入力なら検査を直し（直した commit の確かめは、一覧の行が通って直したときと同じ）、攻めるために組み立てた入力でしか起きないなら、同じく守らない範囲の文で閉じる。(d) を頼むのは、頼まれなかった子が 2 人とも、出典の環境が無いと、再現を試さずに unknowns へ回したため。収束は、一覧の全行に落ちる検査か、守らない範囲の文があること。証拠には、子に攻めさせた commit と一覧を書く。(6) コード（テスト・検査のコードを含む）と、エージェントの動きを決める文（指示ファイル・スキルなど）・検査の対象を決める設定（除外の一覧など）を変える変更では、push・PR の前に、(5) とは別に、変更の危険度に応じて `interrogate` を通す（低なら省く。危険度と深さ・周回の止め方は `interrogate` の 5）。(5) の子は主張に書かれていない性質（足したコードの異常系、テストの壊れにくさ、主張の外の MUST、実装より広い条件の文）に向かず、(5) を済ませたことは届けてよい理由にならない。指摘は主審として「対応する」（同じ変更で直す）・「記録のみ」（直さない理由を入口の返答の 2 に書く。PR のレビュアーが「この PR で直さなくてよい」と書いた指摘は、`playbook-deliver` の「PR のレビューに応える」に従う）・「退ける」に決め、どこまで直すかを利用者に選ばせない。仕様の矛盾か製品上の選択を含む指摘だけを、入口の返答の形の 4(b) で返す。利用者に頼まれた審査の報告は、利用者が決める。次の周とその範囲、前提を疑う時期、主張を破る経路の閉じ方は `interrogate` の 5・6。

| 対象 | 最初に確かめること | 残す検証の形。言い過ぎない境界 |
|---|---|---|
| 文書 | 読者がその手順で目的を達成できるか | リンクと例の検査。書いたとおりの手順の実行（文書が読者を分ける道筋ごと。実行していない道筋は名前で残す。期待結果と説明の文を出力と照らした台帳。`playbook-docs-skill` の 5）。前提を知らない別セッション（読者役）での追試（規則・方針は、当てはまる場面の問いに答えさせる。`playbook-docs-skill` の 5）。文章が整っているだけでは成功にしない |
| スキル・手引き | 意図した依頼で使われ、意図しない依頼で暴発せず、必要な行動に至るか | 新しい CLI セッションで入力と成果物を観測する。使う例・使わない例・制約を守る例。キーワードの有無の検査にしない。スキル・指示ファイルの文を読んだモデルがどう動くかを主張に書くときは、下の「モデルの挙動に頼る主張」 |
| 知識ベース | 出典をたどれ、必要な情報を見つけ、矛盾を区別できるか | リンク・出典・重複の機械検査。代表的な問いからの検索と説明の確認。外部事実の真偽をリンク検査で証明したことにしない |
| 解析 | 計算と比較が再現でき、評価対象へ都合よく合わせていないか | データの範囲・乱数・入力のバージョン・数値の不変条件・時間分割・未使用データでの評価。スクリプトの成功と予測の有効性を分ける |
| コード | 実際の利用箇所で要求した振る舞いになったか | 既存テストに加え、CLI・API・UI の利用経路と失敗例を実行する。言語別の仕組みを bb-writ 側に増やさない |

共通にするのは「依頼から成果へ進む体験」で、言語名や検査コマンドではない。その対象の通常の開発方法（package script・devcontainer・CI の定義・既存の検査）をそのまま使う。初めて見る言語や道具でも、bb-writ を直さずに進める。検証は、利用者が成功を観測する場所から決める。

**モデルの挙動に頼る主張。** 指示ファイル・スキル・プロンプトの文を読んだモデルがどう動くかを述べる主張（「この文が効く」「スキルがこのファイルを読む」「この依頼でこのスキルが使われる」）は、求めることの説明（仕様。「このスキルは〜を返す」）でなく、モデルが実際にそう動くと書くもので、どこに書くときも（返答・PR の本文・commit のメッセージ・文書・コードのコメントや docstring）、1 つのモデルの 1 回の実行で確かめたことにしない。モデルの挙動は、同じ入力でも、実行ごとにもモデルごとにも変わる。「1 回実行しました」と添えても、読む人には効く根拠として渡る（Sonnet 系の既定の 1 回で、スキルが README を読むと PR に書き、レビュアーの Opus 系の既定では読まなかった）。何が出れば成り立ったと数えるかは、条件 (1) のとおり、流す前に決める。流すモデルは 2 つ以上にし、1 つは利用者が使うモデル、ほかはそれと大きさか系統の違うモデルにする（同じモデルの別名や版の違いだけにしない）。利用者が使うモデルは、依頼と、対象のリポジトリの設定・指示ファイル・CI の定義から読む。どこにも無ければ、利用者に聞かず、いまのホストで選べる、互いに大きさか系統の違う 2 つ以上で流し、「利用者が使うモデルは分からなかった」と主張に添える。確かめるモデルの一覧は、bb-writ は決めない。モデルごとに 3 回以上、毎回新しいセッションで流す。モデルは毎回名指しして渡し、CLI や設定の既定に任せない（既定は設定ごとに違う）。各回、実際に動いたモデルの ID と、流した構成（入っていたプラグイン・スキル・指示ファイル）を記録する。名指しと違うモデルで動いた回は、実際に動いたモデルの回に数える。挙動の主張の回数に数えるのは、主張する挙動そのもの（ツールの呼び出し・成果物・出力）を観測した回だけで、その回は利用者が打つ形の CLI の起動で流す（launcher の子は依頼文に文を足すので、この回には使わない）。文書だけを渡して問いに答えさせた回（読者役など。launcher の子でよい）は、「問いにこう答えた」という主張にだけ数える。数え方を決める前の回、名指ししなかった回、新しいセッションでなかった回、エラーで終わった回は数えない（エラーの回は流し直す）。確かめる対象の文を変えたら、変えた文で流し直す（前の文の回は数えない）。主張には、モデルごとの流した回数と成り立った回の数を添える（「<モデルの ID> で 3 回中 3 回、<別のモデルの ID> で 3 回中 1 回」の形）。2 つ以上のモデル・各 3 回以上で流し、全部のモデルの全部の回で成り立ったときだけ、流したモデルの範囲で成り立つと書く。範囲を付けない「効く」は、そのときも書かない。割れたら割れたとおりに書く（揺れる文を効く形に直す方法は、ここでは決めない）。この条件に足りない結果は、「<モデルの ID> で n 回中 m 回、この結果だった」の形に狭めて書き、効くとは書かない。ほかの確かめの観測（読者役の答え、`playbook-eval` の比べ）の報告は、この形で足りる。挙動を変更の成果として書くとき、条件に足りないままにしてよいのは、流せないとき（モデルを使えない〔権限が無い、利用枠が尽きた、名指ししても別のモデルで動く〕、構成を手元で再現できないなど。費用と時間は理由にせず、入口の「子への委任」の、試す作業の所要の見積もりで縮めるときも、モデルごとの 3 回は減らさない）だけ。そのときも、流せるモデルでは各 3 回以上流し、流せなかったモデルの名前（分からなければ「ほかのモデルでは流していない」）を主張に添える。文書やリポジトリの規則がそこに回数を書かせないときは、回数は規則の許す場所（PR の本文・commit のメッセージ・リポジトリが決めた実測の置き場）に書き、その文書には、流したモデルの範囲を付けた主張と上の 2 つの添え書き（利用者のモデルが分からなかった・流せなかったモデル）を書く（割れた・条件に足りないときは、そのことを回数を書かずに書く）。既に書かれている主張は、その主張の文を書き換える変更のときにそろえる（同じ箇条・同じ段落のほかの文を変えただけなら、そろえない。この決まりより前に書かれた主張を、一度に直すことは求めない）。書き換えるときに元の回数が記録に無ければ、流し直すか、「確かめた範囲は記録に無い」と添える。作業の記録の「済んだことと証拠」には、モデルごとの回数・成り立った回の数・各回の出力の道筋を書く。

**CI を試し場にしない。** 入口の手順 3 で仕様を読み、手元で確かめられる部分（BSD と GNU のコマンド、macOS 標準の bash 3.2、一時ディレクトリの symlink などの差を含む）は手元で潰してから CI に出す。調べるための job・step・commit を、push・pull_request で動く workflow に足さない。確かめるための push を重ねない。push のたびに全部の job が動き、private のリポジトリでは macOS の runner の分単価が Linux の約 10 倍になる（2026-01 からの価格表で $0.062 と 2-core の $0.006）。CI は仕上がった変更の確かめに使う。手元に無い環境（対象の開発者が macOS を使うなど）での確認が必須なら、手元で潰した後に、まとめて 1 回にする。その 1 回は、push で動かない起動（`workflow_dispatch` だけで動く workflow など）か、その環境の利用者の手元での実行で行う。workflow を足す・変えることが依頼に無ければ、聞く（入口の手順 1）。出す前に起動条件を読む。PR のブランチへの 1 回の push で、push と pull_request の両方の起動条件が同じ job を動かすことがある。それで落ちたら、ログと仕様から原因を絞って手元で直す。次の 1 回の前に、落ちた差と読んだ仕様を記録に書く。

**CI の結果まで見る。** push・PR の後は、その commit の CI が終わるまで `gh run watch --exit-status <id>` で待ち（1 回の呼び出しに Bash の時間の上限を 10 分渡し、`timeout 540 gh run watch …` のように、終われば返り、終わらなければ約 9 分で返る形でくり返す。呼び出しのたびに会話の全部を読み直すので、3 分ごとに確かめると、同じ CI を待つ費用が 3 倍になる）、job ごとの結果を返答の 3 に書く。終わる前に「済んだ」と書かない。cancelled（時間切れなどの打ち切り）も失敗と同じに扱う。Release は CI が通った commit にだけ出す（`work.py op run` の release は、終わっていない・通っていない実行があれば拒否する）。workflow の `timeout-minutes` を決める・変えるとき、打ち切りが出たときは、`gh run list`・`gh run view` で最も遅い OS の成功した実行の時間を見て、その最長の 3 倍以上にする。macOS の runner は Linux より遅く、日によって 1〜2 割揺れる（上限を実行時間ぎりぎりに置くと、全部通るテストが打ち切られる）。打ち切りに、テストを削って合わせない。

完了の証拠は、確認した成果物の版（commit・PR・ファイルのパス）、検証の手順と入力、結果、残った範囲を結び付ける。検証の後に成果物や前提が変わったら、影響する証拠を取り直す。出力はコマンドと観測をそのまま載せる。長いものは、担当を取った仕事では `claim` の出力の `note.evidence_dir`、担当を取らない読むだけの仕事では `~/.local/state/bb-writ/notes/<owner>__<repo>/` に置いてパスを示す。`/tmp` は消えるので証拠に使わない（そこにしか書けない環境なら、そう書く）。要約で置き換えない。変更を届けるとき（PR など）は、本文に「なぜ・何が変わるか・範囲・壊れうる所・どう確かめたか・戻し方」を書く。必須の PR や CI を作るために仕事を変形させない。

## 成果物の検証（push・PR の前に必ず 1 回。危険度の宣言によらない。前例を写す変更と、人が読む文書の文だけの直しを除く）

**人が読む文書の文だけの直し。** README・手引きの文書・CHANGELOG など人が読む文書で、差分がコードブロック・インラインのコード・コマンド・設定の値・数値・リンク先を変えない直し（言い換え・並べ替え・段落の移動・節の分け直し・表記のそろえ。移した先でも同じ字のままなら、変えていない）は、成果物の検証役を立てず、`playbook-docs-skill` の 5 の手順の実行と台帳も省く。リポジトリの文書の検査を流し、読者役 1 人に、読者が目的に届くかを問いで確かめさせる。返す前の判定の監査役には、この扱いにしたことを伝え、差分がコードブロック・インラインのコード・コマンド・値・数値・リンク先を変えていないかも判定させる（この変更で、監査役が唯一の独立した確かめになる）。スキル（SKILL.md）・指示ファイル（AGENTS.md・CLAUDE.md）は、子が読んで動きを決める文なので、この扱いにしない。規則を足す・変える直し（表記・用語の基準や使わない語の行を書くなど。`interrogate` の 1）も、文の言い換えでないので、この扱いにしない。差分がこの形を超えたら、普段どおりにする。

**前例を写す変更。** 依頼か作業の記録が、同じ種類の前の commit（前例）を名指しでき、差分が前例と同じファイルの同じ箇所で値だけを進める変更（バージョンの固定の更新、同じ形の記録の行の追加など）は、成果物の検証役と条件 (5) の子を立てない。前例が流した確かめのコマンド（前例の commit・PR の本文・リポジトリの手順にあるもの）を流し、`git diff <前例>^ <前例> --stat` と自分の差分の `--stat`・hunk を並べて、同じ形に収まることを証拠の置き場に残す。返す前の判定の監査役には、前例の commit と、並べた結果の道筋を渡し、差分が前例の形に収まっているかも判定させる（この変更で、監査役が唯一の独立した確かめになる）。差分が前例の形を超えたら（前例に無い文・検査・ファイルを足した）、この扱いをやめて、下の検証役を立てる。前例の外で見つけたこと（前例のときには無かった事実、足したくなった説明・検査）は差分に入れず、入口の返答の 4 に書く。

届ける commit を checkout した未 commit の変更が無い作業場所を `--cwd` にして、`delegate` の launcher で読み取り専用の子を 1 人立てる。いま動いているホストが Claude Code なら `--model opus --effort high` を渡す（表の読み取り専用の段と違う段が要る場面。違うモデルで動いたときの `model_substituted` は返答の 3 に書く）。Codex・Grok Build なら、モデルを渡さず表のまま立てる（`--interrogate`・`--audit` は付けない。危険度が中・高のときの `interrogate` と、返す前の判定は、これとは別に通す）。この子は、書いた子とも指揮者とも別の文脈で、成果物をレビュアーの目で読む。launcher の子は GitHub を読めず、対象の外は読めるとは限らないので、Issue の本文・依頼の文・PR の本文の下書きは、依頼文の中に資料として引用で写す。作業者の報告を正しいものとして渡さない。依頼文は次の形にする（＜＞の中を埋める）。

> あなたは、このリポジトリの変更を、人の PR レビューに出す直前に検証する役です。書いたのは別の作業者で、あなたはこの成果物を初めて見ます。作業者の報告（PR の本文・commit の件名・コメント）は主張であって、正しいとは限りません。
>
> 変更は `git diff ＜基点＞..HEAD`（commit は `git log ＜基点＞..HEAD`）。規則は README・AGENTS.md・CLAUDE.md にあれば読む。背景の資料は、この依頼文の末尾にある。
>
> 頼むこと: この変更をこのままレビューに出したら、注意深いレビュアーが指摘するはずの点を、全部挙げる。差分の行だけでなく、差分が前提にする周りのファイルも読む。
>
> 見る観点:
> 1. 変更が書いた主張（文書・README・コメント・テストの名前・PR の本文）を 1 文ずつ、実物（コード・設定・リポジトリのほかの文書・Issue の要件）と照らす。食い違い、言い過ぎ、根拠の無い一般化、存在しないものへの参照。
> 2. Issue の要件・完了の条件・範囲外の定めと、変更の範囲。
> 3. 対象と書いた環境・利用者（OS・シェル・ロケール・道具の入れ方）ごとに、手順やテストが本当に成り立つか。確かめていない環境についての主張。
> 4. 足した・変えたテストや検査が、名前の言う性質を本当に確かめているか（別の理由で通らないか、検出しない形は無いか、途中で止まったのに成功で終わらないか）。
> 5. 要らないもの、重複、後の保守の手間（同じことを 2 か所で持つ、後で直し忘れる文）。
> 6. リポジトリのほかの場所との一貫性（名前・表記・題・数）。
> 7. 変更が規則を決めているなら（差分の外の本文・コード・設定・検査も従うべき決まりを足す・変える。表記・用語の基準、使わない語・採る語の一覧の行、lint などの検査のルールの有効・無効・除外、指示ファイル・スキルの決まり）、決めた規則を差分から 1 文ずつ拾い、規則ごとに次の 3 種類を自分で探す。(i) 既存の本文・コードのうち、その規則が当てはまる同じ種類の箇所。規則に反する箇所が残っていないかを見る（ツールが検出しない形の規則は、検索の式を自分で作って探す）。規則の文が条件を複数持つときは、条件ごとに探す（「全角のかっこを使い、前後にスペースを入れない」なら、半角のかっこと、前後のスペースの 2 つ）。(ii) 同じ種類の項目を守っている既存の検査（禁止語のテスト、対象の一覧を持つテストなど）。変更が一覧・表に足した項目が、その検査にも足されているかを見る（足さないと、規則に反しても何も落ちない）。(iii) その規則に関わる指摘を出すツールの設定（この変更が有効にしたルールだけでなく、前から有効な設定・別のプリセットも）。ツールの指摘が規則と矛盾しないか、書く人がツールの指摘のとおりに直すと規則に反する形にならないか、規則の文が「例外はこれだけ」と書くとき前からある設定がそれと食い違わないかを見る。規則を採った・有効にした理由が、その規則を見直す人の読む場所（表の行など）から読めず、外しても落ちる検査が無い状態も挙げる。挙げ方は、規則ごとに、探したコマンドと、見つけた場所か「無し」（この観点は、見つけた場所が無くても書く）。
>
> 実行できるテスト・検査は、`mktemp -d` で `$TMPDIR` の下に作ったディレクトリに写して動かしてよい（1 つずつ。並列にしない）。動かせなかったものは、そう書く。全テストは、下の「全テストの結果」の commit が自分の `git rev-parse HEAD` と同じなら、流し直さなくてよい（結果が無いか違えば流す）。差分に関わるテストと、攻めるための注入に時間を使う。少なくとも 1 本は流し、実行の欄を `yes` にする。
>
> 報告の形: 指摘ごとに、重さ（直すべき / 直した方がよい / 軽微）、場所（ファイル:行）、何が問題か、根拠（読んだ行・実行した結果）。推論だけで確かめていない指摘は「推論」と書く。ほめない。指摘が無い観点は書かなくてよい（7 を除く）。
>
> 全テストの結果: ＜指揮者が、未 commit の変更が無い状態でこの commit の全テストを流し、`git rev-parse HEAD`・コマンド・終了コード・件数・出力の末尾を写す。流していなければ「なし」＞
>
> 資料: ＜Issue の本文、依頼の文、PR の本文の下書き＞

指摘は、指揮者が 1 回で仕分ける。直す前に、記録の「指摘の扱い」の欄へ、指摘ごとに書く。

- **直す:** 実物で確かめて正しかった指摘のうち、事実の誤り、文と実物・Issue の要件・リポジトリのほかの記述との食い違い、確かめていない環境についての言い切り、テストが名前の言う性質を確かめていないこと、要件の満たし漏れ、依頼の範囲からの外れ。重さが軽微でも直す（直すのが安く、レビュアーが拾う）。確かめていない環境についての主張は、その環境で確かめるか、確かめていないと書き直す。規則の当てはめ（観点 7、上の「確かめる」）で見つかった、変更が足した項目を守る検査の欠け（(ii)）と、規則の文と既存の設定の矛盾（(iii)）は、同じ変更で直す。既存の箇所の違反（(i)）は、同じ仕事の中で直すか、規則の文に、まだそろえていない範囲を書いて閉じる（決め方は `interrogate` の 5 の「指摘に重さと由来を付ける」と同じ）。ただし、PR のレビュアーが「この PR で直さなくてよい」と書いた指摘と同じものは、`playbook-deliver` の「PR のレビューに応える」に従う。
- **範囲の外れは、言い直さずに外す:** 指摘の対象が、依頼（前例を写す変更なら前例の形）の範囲の外に自分で足した文・検査・仕組みなら、言い直さず、その部分を差分から外して入口の返答の 4 に移す（言い直すと、直した文に次の指摘が付いて周が重なる）。
- **直さない:** 確かめて誤りだった指摘、好みだけの指摘、将来に備えた仕組みの提案、攻めるために組み立てた入力でしか起きない指摘（`interrogate` の 5 の Important に当たるものは直す）。理由を記録に書く。

扱いはこの 3 つだけで、直しも外しもせず、「直さない」の種類の理由も無いままでは閉じない（「記録のみ」「検討」「後で決める」と書いても、中身で決まる。PR のレビュアーが「この PR で直さなくてよい」と書いた指摘と同じものだけは、上の「直す」のとおり、`playbook-deliver` の「PR のレビューに応える」に従う）。「この変更が決めていないこと」「後の変更で決める」は、直さない理由にならない。実物で確かめて正しく、「直す」の種類に当たる指摘は直す（決めて書くか、決めていないこと・守らないことを成果物の文に書く）。対象が依頼の範囲の外に自分で足したものなら、外す。読者役（`playbook-docs-skill` の 5）の指摘も、同じ仕分けで決める（検証役と読者役の指摘を「記録のみ（この PR が決めていないこと）」で閉じて届け、同じ指摘が人のレビューに出た。#91）。

直しは 1 つにまとめる。成果物を書いたのが書く子なら、その子に `--resume` で直させる（数行の文面は自分で直してよい）。自分で書いたなら、自分で直し、直しのために書く子を新しく立てない。直した後は、検証役を立て直さず、指揮者が直しの差分を読み、確かめ方のコマンドを実行して確かめる。文だけの直し（主張を狭める・削る・言い換える。テストのファイルのコメントも含む。エージェントの動きを決める文の、動きを変える直しは除く。`interrogate` の 5）は振る舞いを変えないので、確かめ役を立てず、指揮者が差分を読み、その主張を縛る検査があるかを確かめる（条件 (4)）。直しが振る舞いを変えたときだけ、直した commit で確かめ役（読み取り専用の子）を 1 人立て、直しの差分だけを見させる。届けるときの `--reviewed` には、危険度が低なら、最後に読み取り専用の子が `ok` で返った commit を書く。中・高なら、`--interrogate` の審査役が `ok` で返った commit を書く（検証役・確かめ役の記録だけの commit は、関門が拒否する）。どちらも、その後の差分が文面だけなら `--delta 低` を添える（エージェントの動きを決める文の、動きを変える直しは文面だけに数えない。`interrogate` の 5）。

## 返す前の判定（遵守の監査）

push・PR の前と返す前に、入口の返答の 2〜4 の下書き（4 が無ければ「無し」）と作業の記録・差分を、新しい文脈の子に渡す。届ける commit を checkout した未 commit の変更が無い場所を `--cwd` にし、`delegate` の launcher に `--audit` を付けて読み取り専用で立てる（`work.py` は、`--reviewed none:` でも、HEAD を対象にしたこの記録が無い push・pr を拒否し、統合する commit を対象にしたこの記録が無い `integrate` も拒否する。`integrate` だけは、専用ログインが無いせいでこの子を起動できなかった `unavailable` の記録（`no_login` が真）も数える。`none:` は interrogate を省く宣言で、子を省く宣言ではない）。子には次を判定させ、下書きも作業者の報告も正しいとは伝えない。launcher は、`--audit` の子の依頼文の末尾に、この節の項目をすべて判定する約束を足す（依頼文が項目を「差分の各文」などに狭めても、届くように。親が書いた依頼文が範囲を「差分の各文」に狭め、監査役はほかのファイルとの名前の食い違いを範囲外として通した）。

- 遵守: 使ったスキル（入口・この手引き・課題の手引き。名前を渡し、子が本文を読む）から、この変更に当てはまる確かめ方の要求を全部挙げ、要求ごとに「満たした」「省いた（記録に理由がある）」「別のもので代えた（代えたもので要求を満たすか）」「省いたが記録に理由が無い」に分ける。根拠にしたスキルの文と、記録の行・委任の記録（立てた子の out の `prompt.md` の依頼文と `report.md`）を引かせる。記録の要約だけで判定させない（「審査役 2 人が ok」とだけ書いた記録からは、何を頼んだかが分からない）。Claude Code の監査役は、その場所の作業の記録・その場所を `--cwd` にした子の out・bb-writ のスキルを読める（ほかの場所の記録は読めないので、記録の置き場の外に書いたものは中身を依頼文に写す）。対象の検査（文書の検査・テスト）も子に実行させる（指揮者が同じ commit で全テストを流したなら、成果物の検証役の雛形の「全テストの結果」と同じものを依頼文に写し、子には、その commit が自分の HEAD と同じなら全テストを流し直させず、差分に関わるテストを流させる（少なくとも 1 本。実行の欄を `yes` にさせる）。全テストは手元で約 600 秒かかり、子ごとに流し直すと、その時間が子の数だけ重なった。読んだだけの報告は `not-run` で、関門に数えない。子の sandbox のせいで実行できないときは、親が HEAD で実行した証拠を記録に書き、`--not-run` を宣言して届ける。監査役は、その証拠が子の実行の代わりになるか（写し方を教えれば子が動いた場面でないか）を判定する。`playbook-deliver`）。
- 文の照合（手順の文書を変えたとき）: 変えた手順の文書の全体から、コマンドやオプションの働き・表示されるもの・かかる時間や数値・後に残るものと消えるもの・名前・状態を述べる文を全部拾い、証拠の実行の記録と書き手の台帳に 1 文ずつ照らして、「記録が支える」「記録と食い違う」「記録に現れない」「コマンドが実行されていない」に分ける。同じ名前・数・状態を持つほかのファイル（差分の外も）との食い違いも挙げる。記録が支えない文は、書き手が何で確かめたか（実行・出典の節）が記録にあるかを見る。遵守の判定だけでは、照合を求める規則に「実行した」記録があれば満たしたことになり、文ごとの真偽は見ない（実行の記録に反証があった `detached HEAD` の文を、監査を 18 回立てても誰も挙げなかった。#36）。
- 4 の各項目と、2 に書いた「残した点・守らないこと」の各項目が、実行・読み・試作・別の環境・同じ仕事での修正（範囲の外で見つけた穴も。PR のレビュアーが「この PR で直さなくてよい」と書いた指摘は、`playbook-deliver` の「PR のレビューに応える」に従う）・既定での決定（戻せる選択）のどれで閉じられるか。閉じられないなら、確かめた制約か、目的・規則・仕様から決まらない戻せない選択か。意図して守らない振る舞いは、テストか文に示されていて依頼の目的に反しなければ閉じたものとする。
- 危険度の宣言: 届ける変更の全体（依頼文が示す基点から HEAD まで。立て直しでも差分に限らない）が、`interrogate` の 5 の基準でどの段（低・中・高）に当たるかを、差分の中身（変えたファイルが何か、その変更が誰の動き・どの検査の対象を変えるか）から判定し、最後の JSON の `risk` に書く。作業者の宣言とその理由（「コードの変更が無い」「文書だけ」）をそのまま受けない。`work.py` は、push・pr の `--risk` が、HEAD の監査役が判定した段（割れたら最も高い段）より低ければ拒否する（`deliver` は、この項目では変えない）。
- 指摘の扱い: 作業の記録の「指摘の扱い」の欄の行のうち、成果物の検証役・読者役が出した指摘の行（ほかの子も同じ指摘を出した行を含む）を、記録の行と委任の記録（`prompt.md`・`report.md`）から見分けて判定する（立て直しでも、毎回、これらの行の全部）。ほかの行（`interrogate` の審査役、条件 (5) の子、確かめ役、監査役自身が挙げた点、人のレビュー、bot の指摘）と、PR のレビュアーが「この PR で直さなくてよい」と書いた指摘と同じ行は、この項目では判定しない。扱いは、書いてある語でなく中身で見る（記録の雛形の欄と launcher の案内は「対応する・記録のみ・退ける」の語を並べる）。挙げるのは、成果物で直しても差分から外してもいない行（指摘の一部だけを直した・外した行は、残りの部分で見る）のうち、「成果物の検証」の「直さない」の箇条書きが挙げる種類の理由が書かれていない行（「この変更が決めていない」「後の変更で決める」など）。直した行・外した行と、その種類の理由が書かれた行は、語が何であっても挙げない。理由が種類に当たるなら、理由が十分かまでは判定しない（子の報告と照らして、明らかに種類が違うときだけ挙げる）。

審査の深さと周回は `interrogate` の 5 で決まり、判定では変えない（危険度の宣言の項目は、深さを変えるのでなく、段を判定して書く）。その止め方で回さなかった周は残りに数えず、3 に書く。依頼に無い外部への送信（push・Release）の許可は、4 (b) の仕事の権限として 1 行で聞く。監査役は、最後の JSON の `deliver` に判定を、`risk` に危険度の段を書く（launcher が監査役の約束に足す）。`no`（差し戻し）は、届ける成果物（文書・コード・テスト・設定・commit の本文）に実物と食い違う文や誤りがあるか、スキルが求める確かめの手順そのものを行っていないか、成果物の中で閉じられる残りがあるときだけ。指摘の扱いの項目で挙がった行があるときは `no` にする（その指摘は、成果物の中で閉じられる残りで、作業の記録の整えに数えない。仕分けし直して直す・外すか、仕分けに在る理由を書いて閉じる）。手順は行ったが記録に書いていない、作業の記録・返答の下書き・証拠の置き場の整えだけなら `yes` で、整える点を報告に並べる（commit の本文は、直すと HEAD が変わって監査の記録が数えられなくなるので、整えに入れない）。`work.py` は、判定を書いた監査役の記録のうち `deliver: yes` のものだけを push・pr と `integrate` の関門に数える（本文で差し戻した監査は、`status` が `ok` でも通らない。同じ commit に `yes` の記録が 1 件でもあれば、その後の `no` では止まらない）。`no` なら、挙がった項目を閉じてから、もう一度判定させる。`yes` で挙がった整える点は、指揮者が直して記録の指摘の扱いの欄に書き、監査役は立て直さない（記録や下書きの整えのたびに立て直すと、監査が 3 回目以上まで続いた）。子の判定を退けるときは、その理由を返答の 3 に書く。遵守で「代えた」「理由が無い」と挙がった要求は、記録の指摘の扱いの欄に書き（push・pr はこの欄が空なら拒否される）、対応するなら要求どおりにやり直し、直した commit で監査役を立て直す。

監査役は、HEAD をもう動かさないと決めてから立てる。最後の審査役・確かめ役の指摘を記録の指摘の扱いの欄に書き、直しを commit し終えてから立て、審査役と同じコマンドで続けて立てない（続けて立てると、監査役は毎回、直前の指摘の扱いが記録に無いことを挙げる）。task start の作業場所で、統合先から分かれた後に `SKILL.md`・`AGENTS.md`・`CLAUDE.md` を変えたのに、その作業場所の読者役（`--reader` で立てた子。`playbook-docs-skill` の 5）の記録が無ければ、launcher は監査役を起動しない。読者役を省くなら `--audit` に `--no-reader <理由>` を付け、監査役がその理由を遵守の項目で判定する。立て直すときは、前の監査の out と、前の監査が見た commit を依頼文に書き、前の監査が挙げた項目が閉じたかと、その commit から HEAD までの差分だけを判定させる（その差分で使うスキルが増えたなら、その要求も含める）。毎回全体を初めから監査させると、別の所を挙げ続けて止まらない。ただし文の照合は差分に限らず、毎回、変えた手順の文書の全体を照らさせる（差分だけを見る立て直しは、前の監査が見逃した文を二度と読まない。途中の commit で入った誤りが、監査がすべて `ok` のまま残った。#37）。危険度の宣言も、毎回、届ける変更の全体で判定させる。指摘の扱いも、毎回、成果物の検証役・読者役の指摘の行の全部を判定させる。`--delta 低` で届けるときは、審査を通した commit から HEAD までの差分が、振る舞い・主張を変えていないか（テストを足す・強める直しなら確かめの子を立てたか）も判定させる（`work.py` は宣言の真偽を見ない）。立て直しでは、この `--delta` の差分の判定も前の監査の commit から HEAD までに限る（その前は前の監査が判定した）。
