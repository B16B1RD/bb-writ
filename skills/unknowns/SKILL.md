# unknowns — 実装前の探索セッション

プロンプトや計画は「地図」、実際のコードベースと制約は「現地」。その差分 = unknowns が大きいまま実装に入ると、手戻りが高くつく。このスキルは、実装前の安い段階で unknowns を減らすための探索セッションを回す。

出典: Thariq Shihipar "A Field Guide to Fable: Finding Your Unknowns"（https://x.com/trq212/status/2073100352921215386）

unknowns は 4 象限で捉える:

| | 既知 | 未知 |
|---|---|---|
| **既知の** | プロンプトに書けること | まだ決めていないと自覚していること |
| **未知の** | 当たり前すぎて書かないが、見れば分かること | 考慮すらしていないこと |

このスキルの仕事は、右列（既知の未知・未知の未知）と左下（見れば分かる系）を、実装より安いコストで左上に移すこと。

## 大原則

- **探索と実装を混ぜない**。このスキルの実行中は本実装のコード変更を行わない。実装に進む機運が高まったら、探索サマリを出力してセッションを終える。実装は別セッション・別ワークフローの仕事
- **質問する前に、その問いを分類する**（`principle-two-human-roles`）。「どの方法にするか」「どうすべきか」「どう振る舞うべきか」を聞きたくなったら、聞く前に次のどれかを決める
  - 読めば分かる（コード・既存の利用箇所・文書・Web） → 調べて答える
  - 動かせば分かる（振る舞い・時間・メモリ・出力・見た目・性能、eval で差が出るかどうかも含む） → 人に聞かず、使い捨ての実験やプロトタイプで観察して決める（ステップ 2 のプロトタイプ）
  - どの調査・実験でも決まらない、ユーザーの好み・製品上の選択・優先度 → これだけを聞く
  - 不可逆な操作や依頼に無い外部への送信 → 権限として聞く
- **同意は unknowns を減らさない**。ユーザーの案に欠陥や見落としがあれば、根拠とともに指摘する。追従的な応答はこのスキルの目的そのものに反する
- **問いを残して終わらない**。探索の目的は unknowns を減らすことなので、問いを積み残したサマリは本末転倒。セッション中に浮上した問いは「問い台帳」に記録し続け、終了前に全件をステップ 4 の決着ルートのどれかで閉じる。ただし**もみ消しは禁止**: 問いを黙って消す・言い換えて目立たなくする・ユーザーに見せずに既定値で決めることは、問いを残すより悪い
- **ユーザーが応答できない環境**（ヘッドレス実行など）では、質問の代わりに推奨案で仮決定して進める。仮決定した点は探索サマリの「残存」に、推奨案・その根拠・覆った場合の影響・確認方法を添えて載せる（裸の問いとしては残さない）
- **任されたとき**（「任せる」「寝るから進めて」「全部決めて」）は、任された範囲の判断を決めて進め、決めたことを報告する。ユーザーにしか決められない選択も止まらずに既定値で進め、その既定値・根拠と、「代わりにこう言えば変えられる」を平易な文で書く。戻せない操作と、ユーザーが名指しした関門だけは、任されていても聞く
- **返事は自分の言葉で受ける**。「A と返して」「OK と打って」のような合言葉を返させない。聞くときは問いと推奨案を示し、ユーザーが普通の文で答えられる形にする（AskUserQuestion の選択肢は使ってよい）

## 進め方

### 0. 出発点の把握

まずユーザーの現在地を掴む。すでに会話にある情報と、リポジトリを読めば分かることは聞き直さない。それでも足りなければ 1〜2 問だけ:

- 何を作りたい / 解決したいか（一言で十分。曖昧でもよい）
- 対象ドメイン・コードベースへの習熟度（unknowns の在り処を推定する材料になる）
- すでに決めていること / 決めていないと自覚していること

「よく分かっていない」という状態自体が正常な入力。ここで要件を固めようとしない。

### 1. テクニックの選択と提案

状況シグナルからテクニックを選び、「この順で探索するのを提案します」と一言添えてから始める。ユーザーが特定のテクニックを指定したらそれに従う。複数の組み合わせ・往復が普通で、1 つで終わることのほうが珍しい。

| シグナル | テクニック |
|---------|-----------|
| 領域・コードベースが未知。「何を聞けばいいかも分からない」 | ブラインドスポットパス |
| 方向性が複数ありえる。スコープや打ち手が発散している | ブレインストーミング |
| 見た目・UX・体感が判断材料。「見れば分かる」 | プロトタイプ |
| 振る舞い・時間・出力・性能で決まる分岐。「動かせば分かる」 | プロトタイプ（実験） |
| 方向は決まっているが詳細が曖昧 | インタビュー |

### 2. 各テクニック

#### ブラインドスポットパス（unknown unknowns の洗い出し）

ユーザーが考慮していない可能性のある事項を、コードベース・Web の調査に基づいて列挙する。

- 「知らないまま進むと後で高くつく順」に並べる。各項目に「なぜ重要か」「今決めるべきか、後回しでよいか」を付ける
- ユーザーにとって未知のドメインなら、選択肢を評価できるようになる最小限の基礎を教える。目的は知識の網羅ではなく、ユーザーが「何が良いか」の判断基準を持てるようにすること
- 「この変更が触れないが、壊れうる隣接領域は何か」「ユーザーが知らなそうな既存の制約・慣習は何か」を自問して探す

#### ブレインストーミング（方向性の発散と反応）

性格の異なる 3〜5 案を提示する。案は費用の順に並べず、問題を残らず閉じるかで評価する。少なくとも 1 案は問題を残らず閉じる案にし、各案に閉じきらない部分を書く。不完全な安い案は次の対策を生み、安さが残らない。

- 各案: 概要 / 得られるもの / コスト / リスク / この案が合う状況
- 目的はユーザーに**決めさせる**ことではなく**反応してもらう**こと。「A の手軽さは魅力だが B のこの部分は欲しい」という反応こそが、言語化されていなかった要件（未知の既知）を表面化させる
- 全案が同じ方向の濃淡にならないようにする。1 案は意図的に毛色を変える

#### プロトタイプ（見て反応するための使い捨てモックと、動かして決める使い捨て実験）

目的は「見て反応してもらう」か「動かして決める」こと。動く本物を作ることではない。

**動かして決める実験。** 振る舞い・時間・メモリ・出力で決まる分岐は、ユーザーに聞かずにここで決める。

- 決める分岐を 1 文で書く（例: 「200 万行で、全部読んでから集計する方式と 1 行ずつ集計する方式のどちらが時間とメモリで勝つか」）。決める分岐が無ければ実験しない
- 対象のリポジトリの外の使い捨ての場所に、問いを動かす最小のスクリプトを書く。本番の構成・試験・抽象は入れない
- 比べる案は同じ条件で並べて動かし、時間・出力・ログを観察する。観察した結果が判定になる
- 結果（数値・出力）と推奨を示して分岐を閉じる。台帳には「実験で解消」として、コマンドと観察を添えて載せる

**見て反応してもらうモック。** 見た目・UX・体感はユーザーの好みなので、こちらは反応を集める。

- 実データ・実バックエンドに配線しない。fake data で見た目と操作感だけ再現する
- Artifact ツールが使える環境ではそれで HTML を提示する。使えなければ自己完結 HTML（外部依存なし）をファイルに書き、ブラウザで開くパスを案内する
- デザインの複数方向を見たいときは、1 ページに並べて比較できるようにする
- プロトタイプのコードは使い捨てであることを明示する。本実装への流用を前提にしない（流用前提になるとプロトタイプが慎重になり、探索の速度が死ぬ）

**レビューモードをデフォルトで組み込む。** プロトタイプにはフィードバック収集レイヤー（[references/feedback-mode.html](references/feedback-mode.html)）を組み込んだ状態で提示する。組み込み手順・マークアップ・CSS/JS はテンプレートファイル冒頭のコメントに従う。要点:

- 反応してほしい単位ごとにコンテナへ `data-fb="ブロック名"` を付ける（7±3 個が目安）＋末尾に「全体コメント」ブロックを 1 つ
- 各ブロックに「👍 このまま / 🔧 要調整」とコメント欄が付き、画面下の「フィードバックをまとめる」で Markdown を生成 → ユーザーがコピーしてチャットに貼り付ける、という受け渡し。Artifact は CSP で外部送信できないため、この「コピペの橋渡し」であることをページ内バナーに明記する
- 例外: 「複数案からどれが良いか」を一言で選ぶだけの比較ページなど、反応が単純な場合はレビューモードを省略してよい
- プロトタイプ自体が成果物（そのまま第三者に共有する等）になる場合は、レビューモード付きの版とクリーン版を別ファイル・別 Artifact URL で管理する

#### インタビュー（曖昧さの的を絞った解消）

1 問ずつ聞く。回答がアーキテクチャやスコープを大きく変える順に優先する。

- 選択式にできる問いは、選択肢と推奨案を付けて提示する（AskUserQuestion が使えるならそれで）
- 回答が設計をもう変えなくなったら打ち切る。全部聞くことが目的ではない。聞かずに打ち切った問いは捨てずに問い台帳へ残し、ステップ 4 で既定値の仮決定として提示する
- 質問の前に分類する（大原則）。「コードを読めば分かること」「動かせば分かること」を聞くのはこのスキルの禁じ手

### 3. ループと終了判定

反応を受けてテクニックを往復する。各テクニックの途中で浮上した問い（調べきれなかったこと、ユーザーに聞きそびれたこと、後で決めると流したこと）は、その場で問い台帳に 1 行ずつ足していく。終盤にまとめて思い出そうとすると漏れる。本文の但し書きも問いである。「未確認」「要確認」「実装前に確認」「記憶に基づく」のような注記を書いたら、それも台帳に載せる。注記に逃がした問いはゲートをすり抜けやすい。

次のいずれかが終了シグナル:

- 新しい unknown が出なくなった
- ユーザーが方向性を確信した（「これでいこう」）
- ユーザーが実装に進みたがっている

終了シグナルが出たら、サマリの前に必ずステップ 4（問いの決着）を通す。探索したのにサマリがないと発見が引き継がれず、サマリに問いが積み残されていると次の作業者が同じ探索をやり直すことになる。

### 4. 問いの決着（サマリ前の必須ゲート）

問い台帳の全件に、次のルートを 1 つずつ割り当てて閉じる。ルートは上から順に検討する（確実に閉じられるものを優先する）。

| ルート | 対象 | 閉じ方 |
|---|---|---|
| **調査で解消** | コード・Web・ドキュメントを見れば答えが出る（名前の衝突、ツールの制約、既存の慣習など） | 今ここで調べて答えを書く。「実装時に確認」に回さない |
| **小さな実験で解消** | 数分〜数十分の使い捨てスクリプト・プロトタイプで確かめられる | 探索の一部として今やる（使い捨てなので「探索と実装を混ぜない」に反しない） |
| **ユーザーに確認** | 好み・優先度・トレードオフの取り方など、ユーザーの頭の中にしか答えがない（どの調査・実験でも決まらない） | 推奨案を先頭にした選択式で、まとめて聞く（AskUserQuestion なら 1 回 4 問まで。足りなければ 2 回目まで） |
| **既定値で仮決定** | 可逆で、どれを選んでも後で直せる設計詳細 | 決めて進め、推奨既定値・根拠・覆す条件をサマリに書いて報告する。確認の質問にはしない（異論が来たら覆す）。黙って決めない |
| **決定時期を決めて後回し** | 今決めるより後で決めるほうが安く確実（情報が揃うのが後、今決めても覆りやすい） | いつ（どのマイルストーンで）・何をきっかけに決めるか、それまでの暫定扱いを書く。「後で考える」だけでは問いのまま。盲点パスの「今決めるべきか、後回しでよいか」の後者はこのルートで閉じる |
| **検証タスク化** | セッション内では確かめようがない（実機・本番データ・長時間計測が要る） | 下記の 3 点を満たしたときだけ。満たせなければまだ問いのまま |
| **スコープ外** | 今回のテーマに属さない | 理由を書いて報告する（同意を求める質問にはしない） |

**検証タスクは「もみ消し」の温床になりやすい**。「X が可能か → spike で検証」と書くだけでは問いの言い換えにすぎない。次の 3 点がそろって初めて検証タスクとして認める:

1. **手順**: 何を、どの環境で、どうやって試すか
2. **合否基準**: 何をもって可・不可とするか（数値や観察できる事実）
3. **結果ごとの分岐**: 可ならどう進み、不可ならどの代替案に切り替えるか（代替案まで今決めておく）

例: ✗「Avalonia で全画面オーバーレイが滑らかに作れるか → spike で検証」 / ✓「Avalonia で 2 画面・DPI 混在（100%/150%）の全画面オーバーレイを表示し、ドラッグ選択中に 60fps を維持できるか測る。維持できれば採用、できなければ WinUI 3 の別ウィンドウ方式に切り替える」

サマリを書き終えたら、本文全体を見直して「未確認」「要確認」「実装時に」「TBD」のような言い回しが決着記録の外に残っていないか確かめる。残っていれば台帳に戻して閉じる。

決着の結果、ユーザーが回答を保留した・ヘッドレスで確認できなかった、などでどうしても閉じられなかった問いだけが「残存」になる。残存には、閉じられなかった理由・推奨案・覆った場合の影響を必ず付ける。

### 5. 探索サマリ

以下の形式で出力する（言語は会話言語に合わせる）。ユーザーがファイル保存や後続ワークフローへの受け渡しを求めたら、markdown ファイルとして保存する。

```markdown
# 探索サマリ: {テーマ}

## 出発点
{ユーザーの当初の問題意識・現在地}

## 確定したこと
{選んだ方向性と、その理由}

## 却下した代替案
- {案}: {却下理由（Why not）}

## 問いの決着記録
- {問い} → {ルート: 調査 / 実験 / ユーザー回答 / 既定値で仮決定 / 決定時期を決めて後回し / スコープ外}: {答え・決定内容。仮決定なら覆す条件、後回しなら決める時期ときっかけも}

## 検証タスク
- {何を確かめるか}
  - 手順: {環境と試し方}
  - 合否基準: {数値・観察できる事実}
  - 分岐: 可なら {進み方} / 不可なら {切り替える代替案}

## 残存（決着できなかった問い）
- {問い}: {閉じられなかった理由} / 推奨案: {案と根拠} / 覆った場合の影響: {影響範囲}
（なければ「なし」と書く。セクションごと消さない）

## 発見した盲点
- {探索で浮上した、当初考慮していなかった事項}

## 成果物
- {プロトタイプのパス / Artifact URL 等}

## 次のステップ
{例: このサマリを添えて `/bb-writ:bb-writ` に実装を頼む / 検証タスクだけを先に実行する}
```

このサマリはそのまま Issue 起票スキルや実装計画の入力として使える粒度で書く。

**bb-writ に渡すとき**は、Issue にしない。サマリを添えて入口 `bb-writ` にそのまま頼む（例: 「この探索サマリのとおりに直して。検証タスクも実行して」）。入口は「確定したこと」と決着した問いから「できたと分かる確かめ方」を組み立て、検証タスクの手順と合否基準をそのまま検証に使う。確かめ方が 1 つも組み立てられないなら、まだ探索が足りない（ステップ 3 に戻る）。

「議事録」ではなく「次の作業者（未来の自分や別セッションの Claude を含む）への引き継ぎ書」として書くこと。
